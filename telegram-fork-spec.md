# Telegram fork-клиент — задача (вариант 2, gateway)

Спека для **отдельного проекта** — форка `telegram-tt`, который встраивается в платформу как iframe рабочего режима менеджера. Контекст и обоснование — [`telegram-plan.md`](./telegram-plan.md) (выбран **вариант 2**: ключ аккаунта на бэке, браузер ничего не хранит и не шифрует). Бэк-протокол шлюза — там же, §«Протокол шлюза».

Платформенная часть готова: виджет `widgets/telegram/telegram-workspace` грузит назначенные аккаунты, рисует свитчер и **брокерит токен** для iframe. Форку нужно реализовать **две стыковки**: (A) хендшейк с родителем через `postMessage`, (B) клиент WS-шлюза.

---

## Принципы

- **Ключ на бэке.** Форк не логинится сам и не хранит сессию: аккаунт уже подключён. Стартовый экран — сразу клиент, не форма входа.
- **Environment-agnostic.** Форк **не хардкодит** ни адрес шлюза, ни токен, ни accountId — всё приходит от родителя в рантайме. Один билд форка работает на любом стенде (dev/stage/prod).
- **accountId не передаётся отдельно** — он зашит внутрь токена. Форк его не знает и не выбирает; выбор аккаунта — на стороне платформы (свитчер), форку приходит уже нужный токен.
- **Один слой схемы.** gramjs-слой форка обязан совпадать со слоем бэка, иначе вход пройдёт, но чаты/сообщения не отрисуются (см. plan §«Главное условие»). Это инвариант — фиксируем версию.

---

## A. Хендшейк с родителем (postMessage)

Родитель (платформа) — брокер токена. Форк в iframe общается с ним только через `window.parent.postMessage`. Все сообщения несут тег `source: 'fanbeast-tg'`; всё остальное игнорируется.

### Сообщения

```
fork → parent:   { source: 'fanbeast-tg', type: 'request-auth' }
parent → fork:   { source: 'fanbeast-tg', type: 'auth', token, gatewayUrl }
fork → parent:   { source: 'fanbeast-tg', type: 'ready', accountId }      // опц., для UX
fork → parent:   { source: 'fanbeast-tg', type: 'auth-error', message }   // опц., для UX
```

- `token` — короткоживущий (~2 мин) gateway-токен; в нём зашит accountId.
- `gatewayUrl` — `wss://…/tg-gateway`; адрес WS-шлюза, к которому форк открывает соединение.

### Что обязан делать форк

1. **На загрузке** (как только готов открывать соединение) — отправить `request-auth` родителю: `window.parent.postMessage({ source:'fanbeast-tg', type:'request-auth' }, '*')`. Родитель в ответ пришлёт `auth`.
   _Почему request-first:_ родитель (cross-origin) не знает, когда iframe готов, и не кладёт токен в URL; токен живёт ~2 мин — минтить его нужно прямо перед использованием.
2. **Провалидировать origin** входящего `auth`: принимать сообщение только если `event.origin` === origin платформы (передать его форку как build/CI-параметр — список разрешённых origin'ов платформы; **не** `'*'` на приём).
3. **Открыть WS** на `gatewayUrl`, первым кадром отправить `{ type:'auth', token }` (см. секцию B). Дождаться `{ type:'ready', accountId }`.
4. **Истечение токена / реконнект.** Если WS закрылся (в т.ч. код `4401` — токен невалиден/отозван) или токен протух — снова отправить `request-auth` родителю, получить свежий `auth`, переоткрыть WS. Никогда не переиспользовать старый токен на новый коннект.
5. **Смена аккаунта.** Родитель может прислать **новый** `auth` без запроса (когда менеджер переключил аккаунт в свитчере). Получив `auth`, форк должен: закрыть текущий WS и открыть новый с новым токеном (переключение на другой аккаунт) — **без перезагрузки iframe**, переинициализировав состояние клиента под новый аккаунт.
6. (Опц.) После `ready` — отправить родителю `{ type:'ready', accountId }`; при фатальной ошибке авторизации — `{ type:'auth-error', message }`. Платформа использует это для UX (сейчас просто логирует).

> Отправлять родителю можно с `targetOrigin: '*'` (содержимое не секретно: `request-auth`/`ready` без токена), но **на приём** origin проверять строго.

## B. Клиент WS-шлюза

Протокол — из [`telegram-plan.md`](./telegram-plan.md) §«Протокол шлюза». Кадры в обе стороны — JSON.

```
fork → gw:   { type:'auth', token }
gw → fork:   { type:'ready', accountId }

fork → gw:   { type:'invoke', id, request }          // request — base64 сериализованного запроса
gw → fork:   { type:'result', id, response }         // response — base64 ответа
gw → fork:   { type:'error',  id, message }

fork → gw:   { type:'invoke', id, request, dcId }    // для файлов — номер целевого дата-центра
gw → fork:   { type:'update', update }               // входящие апдейты, приходят сами

gw → fork:   close 4401                              // доступ отозван / токен невалиден
```

### Что меняется в форке (из plan §«Что меняется в форке», вариант 2)

1. **Транспорт → шлюз.** Вместо рукопожатия с Telegram форк открывает WS к нашему шлюзу; готовность резолвит по кадру `ready`.
2. **Единая точка вызовов.** Точку, через которую проходят все MTProto-вызовы, завернуть на WS: сериализованный запрос → `{type:'invoke', id, request}`, ответ `{type:'result'|'error', id, …}` разбирать как обычно. Свою машинерию подключения к дата-центрам в этом режиме форк **не** использует — её делает бэк.
3. **Апдейты** — вливать `{type:'update', update}` штатным путём форка.
4. **Файлы/медиа** — скачивание/загрузку перенаправить на тот же WS, добавляя `dcId` (номер дата-центра) в `invoke`. (Бэк сам поднимает соединение к нужному DC через прокси аккаунта — учесть, что первый запрос с нового DC медленнее, см. таймауты.)
5. **Вход проходит сам** — первый служебный вызов уходит через шлюз и подтверждает авторизацию; форму логина не показывать.

### Слой схемы

Привести/держать gramjs форка и бэка на одном слое (plan §«Открытые вопросы»: своя сборка gramjs из форка **или** `teleproto`). На расхождении — вход пройдёт, контент не отрисуется. Зафиксировать версию и следить при апдейтах любой стороны.

## Acceptance criteria

- [ ] Форк в iframe на загрузке шлёт `request-auth`, принимает `auth` только с доверенного origin, открывает WS на `gatewayUrl`, проходит `auth`→`ready`.
- [ ] Показывает основной экран (не форму логина); список чатов и история грузятся через шлюз.
- [ ] Отправка сообщения доходит; входящие апдейты приходят и вливаются.
- [ ] Файлы/медиа качаются/грузятся через шлюз с `dcId`.
- [ ] Реконнект/`4401`/истечение токена → новый `request-auth` → новый `auth` → переоткрытие WS.
- [ ] Получение нового `auth` (смена аккаунта в свитчере) переключает клиента на другой аккаунт без перезагрузки iframe.
- [ ] Никакого хардкода gatewayUrl/токена/accountId; никаких прямых соединений с серверами Telegram; ключа в браузере нет.
- [ ] Слой gramjs форка == слой бэка (контент отрисовывается).

## Что отдаёт платформа (готово)

- Iframe `src = VITE_TG_CLIENT_URL` (URL форка), родитель слушает `message` и валидирует origin.
- На `request-auth` минтит `POST /api/v1/telegram-accounts/{id}/gateway-token` → `{token, expiresAt}` для выбранного аккаунта и шлёт `auth` с `token` + `gatewayUrl` (`VITE_TG_GATEWAY_URL`).
- Свитчер аккаунтов в шапке; при смене — новый `auth` под новый accountId.
- Контракт сообщений — раздел A выше (источник правды: `widgets/telegram/telegram-workspace/ui/telegram-workspace-frame.tsx`).

## Открытые вопросы к согласованию

- **Origin платформы для проверки на форке** — какой список (dev/stage/prod) зашиваем в форк как доверенный.
- **gatewayUrl из env vs из ответа минта.** Сейчас адрес шлюза — env платформы (`VITE_TG_GATEWAY_URL`) и передаётся в `auth`. Если удобнее — бэк может класть `gatewayUrl` прямо в ответ `gateway-token` (тогда `TelegramGatewayTokenDto` += `gatewayUrl`), и платформа возьмёт его оттуда. Решить с бэком.
- **Выбор слоя gramjs** (своя сборка форка vs `teleproto`) — за форком (plan §«Открытые вопросы»).

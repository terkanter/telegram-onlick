# Telegram fork — права на удаление и на аватарки: ТЗ для форка

Продолжение [`telegram-fork-roles.md`](./telegram-fork-roles.md): тот же
settings-пуш, тот же конверт `source: 'fanbeast-tg'`, те же правила origin.
Ничего нового в протоколе — блок `permissions` просто вырос с трёх полей до
пяти. Платформенная половина готова, форку остаётся вырезать UI.

## 1. Что изменилось в `permissions`

```ts
{
  source: 'fanbeast-tg',
  type: 'settings',
  blurImages: boolean,
  permissions?: {
    search: boolean,           // telegram_client.search           (было)
    viewUsernames: boolean,    // telegram_client.view_usernames   (было)
    viewAvatars: boolean,      // telegram_client.view_avatars     ← новое
    forwardMessages: boolean,  // telegram_client.forward_messages (было)
    deleteMessages: boolean    // telegram_client.delete_messages  ← новое
  }
}
```

Правила из предыдущего ТЗ действуют без изменений и **распространяются на новые
поля тоже**:

- **блока `permissions` нет → показывать всё (fail-open);**
- каждый пуш **заменяет** состояние целиком;
- смена прав приходит живьём, применять к отрисованному UI без переподключения.

| Флаг `false`     | Что вырезать                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------- |
| `viewAvatars`    | аватарки **собеседников** во всех местах показа                                             |
| `deleteMessages` | пункт «удалить» у сообщения, «удалить чат» и «очистить историю» у чата, удаление отложенных |

## 2. `viewAvatars` — чисто клиентское скрытие

Сервер это право **не проверяет**: аватарки, как поиск и никнеймы, прячет сам
клиент. Если форк не скроет — картинки будут видны, права не сработают.

Скрывать нужно аватарки **собеседников**, во всех местах показа. Сверить по коду
форка; по аналогии с семью местами никнеймов это как минимум: список чатов,
шапка чата, сообщения в группах, профиль, список контактов, форварды, реплаи,
участники группы, результаты поиска, звонки.

Что показывать вместо: тот же плейсхолдер, что уже есть у контакта без фото
(инициалы на цветной плашке). Отдельного «скрыто» состояния не рисуем — это не
ошибка и не запрет, человек просто не должен видеть лицо.

Аватарку **своей анкеты** не трогаем: это не собеседник, и менеджер должен
понимать, от чьего имени пишет.

## 3. `deleteMessages` — скрытие поверх серверного запрета

Здесь порядок обратный: **запрет держит сервер**, скрытие — вежливость.

Без права шлюз не выполняет пять команд:

```
messages.DeleteMessages           сообщение в личке / группе
channels.DeleteMessages           сообщение в канале / супергруппе
messages.DeleteHistory            удаление чата
channels.DeleteHistory            очистка истории
messages.DeleteScheduledMessages  удаление отложенных
```

Сообщение остаётся на месте, соединение живо, в ответ приходит кадр ошибки:

```json
{ "type": "error", "id": 42, "message": "…", "errorCode": "TELEGRAM_MESSAGE_DELETION_NOT_ALLOWED" }
```

Что делает форк:

1. **Прячет пункты удаления**, когда `deleteMessages: false` — все перечисленные
   пути, включая «удалить у всех» / «удалить у себя», если они разведены.
2. **Обрабатывает `TELEGRAM_MESSAGE_DELETION_NOT_ALLOWED`** как ещё один код в
   уже написанной таблице кодов ([`telegram-fork-roles.md` §2](./telegram-fork-roles.md)):
   показать текст, снять спиннер, сообщение оставить на месте. Отдельная ветка
   нужна ровно потому, что незнакомый код даёт общий текст, а тут стоит сказать
   прямо: «Удаление сообщений вам недоступно».

Второй пункт **обязателен, а не подстраховка**: право читается один раз, при
подключении клиента. Пока менеджер не переподключился, снятая галочка ему ещё не
доехала — пункт «удалить» виден, и нажатие получит отказ. Это не поломка,
переписка цела; но без ветки по коду человек увидит общий текст и решит, что
клиент сломался.

**Каждый отказ пишется в журнал** попыток на платформе — вместе с текстом
сообщений, которые пытались удалить. То есть дать пользователю «просто ещё раз
нажать» — значит насыпать в журнал шума; поэтому пункт и прячут.

## 4. Чего форку делать НЕ надо

- Не проверять права самому и не кешировать их между сессиями — единственный
  источник это settings-пуш.
- Не изобретать «серую» аватарку или замок на пункте меню: элемент либо есть,
  либо его нет.
- Не называть в тексте отказа причину сверх того, что прислал сервер.

## Чек-лист приёмки

- [ ] `viewAvatars: false` убирает аватарки собеседников везде; своя анкета не тронута; вместо фото — обычный плейсхолдер с инициалами.
- [ ] `deleteMessages: false` убирает «удалить» у сообщения, «удалить чат», «очистить историю» и удаление отложенных.
- [ ] Отсутствие блока `permissions` = всё видно (для обоих новых флагов тоже).
- [ ] Смена любого из двух прав применяется живьём, без переподключения.
- [ ] `TELEGRAM_MESSAGE_DELETION_NOT_ALLOWED` показывает свой текст и снимает спиннер; сообщение остаётся на месте, соединение живо.
- [ ] Незнакомый код по-прежнему даёт общий текст.

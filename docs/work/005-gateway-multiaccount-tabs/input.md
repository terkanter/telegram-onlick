# Несколько анкет в разных вкладках

Цикл от 24.09.2026. Платформенная половина — [`telegram-fork-platform-multiaccount.md`](../../../telegram-fork-platform-multiaccount.md) в корне репозитория (передаётся в `fanbeast-platform`). План — [`todo.md`](./todo.md).

## Задача

1. **Несколько анкет одновременно.** Менеджер открывает разные анкеты в разных вкладках браузера. Вкладки одной анкеты делят одно соединение с гейтвеем, как сейчас. Вкладки разных анкет полностью независимы.
2. **Исправить поломки, которые есть уже сейчас.** Их нашла разведка, и они не зависят от первого пункта.

## Решения

- **Пул iframe отклонён.** У менеджеров есть трекинг анкет, а пул ещё и нагружает браузер.
- **Быстрое переключение анкет — вне цикла.** Если за него браться, то только переключением внутри одного iframe, отдельным циклом. Пока смена анкеты — это новый iframe с новым адресом, по скорости как сейчас.
- **Анкета приходит в адресе iframe:** `?tgAccount=<id анкеты платформы>`. Имя `account` не годится: оригинальный Telegram Web A разбирает его как номер слота через `Number()`.
- **Контракт аддитивный.** Существующие поля сообщений не меняют смысла, новые добавляются. Без `tgAccount` в адресе форк работает как раньше. Форк и платформа выкатываются в любом порядке.

## Что сломано сейчас

Все iframe форка в браузере попадают в одну группу вкладок, потому что имена каналов и ключей берутся из слота `?account=N`, а в режиме гейтвея он всегда первый. В группе выбирается одна главная вкладка, и только она говорит с платформой и гейтвеем.

1. **Права не работают в ведомой вкладке.** Мост к платформе ставится только в главной вкладке (`initApi`). Ведомая не получает `settings`, поэтому права ролей открыты, размытие выключено, экран «доступ отозван» не показывается. Это так даже для одной и той же анкеты.
2. **Вкладка другой анкеты показывает чужие чаты.** Она получает глобальное состояние главной вкладки.
3. **Главную вкладку можно переподключить на чужую анкету.** `initApi` ведомой вкладки уходит главной, и та пересоздаёт клиент с чужим токеном (`multitab.ts` → `client.ts initGatewayClient`).
4. **Сокет не закрывается при потере роли главной.** `destroyConnection` вызывает `TelegramClient.destroy()`, который не трогает транспорт гейтвея.
5. **Повторное получение роли главной перезагружает вкладку.** `setGatewayAuthHandler` сразу проигрывает сохранённый `latestAuth`, а свежий `auth` без флага переподключения считается сменой анкеты.
6. **Гонка удаляет кеш не той анкеты.** Если анкету сменили, пока идёт переподключение, `auth` новой анкеты уходит в `reinitGateway` старого клиента. Затем проверка пользователя вызывает `dropGatewayCache()` под ключом старой анкеты.

## Контракт v2

Конверт прежний: `source: 'fanbeast-tg'`, те же правила origin. Всё новое действует, только если форк открыт с `tgAccount`.

### Адрес iframe

`<адрес форка>?tgAccount=<id анкеты>#<маршрут>`. Смена анкеты — новый iframe с новым адресом (`key={accountId}`), а не `auth` в открытый iframe.

### Форк → платформа

| Сообщение | Изменение |
|---|---|
| `request-auth` | добавлены `tgAccount` и `requestId` (строка, уникальна на запрос). Шлёт только главная вкладка группы |
| `request-settings` | **новое**: `{ source, type: 'request-settings', tgAccount }`. Шлёт каждый экземпляр форка при старте, и главная вкладка, и ведомая |
| `ready` | добавлен `tgAccount`. `accountId` по-прежнему Telegram user id |
| `route-change` | добавлен `tgAccount`. `accountId` по-прежнему Telegram user id |
| `auth-error` | добавлен `tgAccount`. `accountId` по-прежнему id аккаунта гейтвея |
| `form-content` | добавлен `tgAccount` |

### Платформа → форк

| Сообщение | Изменение |
|---|---|
| `auth` | добавлены `tgAccount` и `requestId` из запроса. Отвечать строго в iframe, который спросил (`event.source`) |
| `settings` | формат прежний. Слать в ответ на `request-settings`, после каждого `auth` и при изменении прав или размытия, в конкретный iframe |

### Как форк принимает `auth`

- **Без `tgAccount` в адресе** — как раньше, включая перезагрузку на неожиданный `auth`.
- **С `tgAccount`:**
  - `auth` с другим `tgAccount` отклоняется с ошибкой в логе;
  - `auth` с `requestId`, которого форк не ждёт, игнорируется с записью в лог;
  - `auth` без полей v2 от старой платформы принимается, как раньше.

## Изменения в форке

Алгоритмы выбора главной вкладки и синхронизации состояния из upstream не меняются. Меняются имена каналов и ключей, а основная работа идёт в модулях гейтвея.

- **`src/util/multiaccount.ts` и `worker/connector.ts`.** Ключ группы берётся из `tgAccount`, если он есть. Каналы `tt-establish_*`, `tt-global_*` и ключ `tt-multitab_*` получают его вместо номера слота. Ключ передаётся воркеру в `name`, потому что воркер сам шлёт `localDbUpdate` в канал группы. Слот `?account=N`, сессии и переключатель аккаунтов upstream не трогаются.
- **`src/util/telegramGateway.ts`.**
  - поля v2;
  - `request-settings`;
  - учёт `requestId`;
  - проверка `tgAccount` во входящем `auth`.
- **Инициализация.** Мост и `request-settings` запускаются в каждом экземпляре при старте, а не только в `initApi` главной вкладки. `request-auth` остаётся за главной.
- **Потеря роли главной.** Транспорт гейтвея закрывается (`GatewayTransport.close`), флаги пост-коннекта сбрасываются. При повторном получении роли старый `latestAuth` не проигрывается, форк просит новый токен.
- **Переподключение с другой анкетой.** Если id аккаунта гейтвея в новом `ready` не совпал с прежним, форк не продолжает на старом клиенте и не удаляет кеш прежней анкеты. Он уходит по пути смены анкеты. Если `tgAccount` из адреса не совпал с id из `ready` гейтвея, форк пишет ошибку в лог.
- **Статус гейтвея в ведомых вкладках.** Остановка из-за отзыва доступа или ошибки должна показываться во всех вкладках анкеты, а не только в главной.

## Что нужно от бэкенда

Кода — ничего. Нужны два подтверждения:

1. **Id в `ready` гейтвея — это id анкеты платформы (UUID).** Подтверждено на dev 24.09.2026: iframe открыт с `tgAccount=3a04d545-…`, гейтвей прислал в `ready` тот же UUID, ошибки о расхождении нет.
2. **Гейтвей переносит короткое перекрытие.** При передаче роли главной вкладки у одной анкеты на секунды бывает два сокета, а после обрыва сети приходит всплеск запросов на токены.

## Вне цикла

- **Быстрое переключение внутри iframe.** Оценка по разведке — 4–6 дней. Там нужно сносить воркер, чистить глобальное состояние и десятки модульных таймеров.
- **Уведомления сервис-воркера по анкетам.** Метки, закрытие и клик сейчас не различают анкеты. В cross-origin iframe веб-уведомления обычно недоступны, и форк играет звук. Проверить и решить отдельно.
- **Кеш медиа по анкетам (`tt-media*`).** Ключи — глобальные id файлов, так что чужого контента не будет. Изоляция нужна, только если начнут отличаться права на аватарки.
- **Гонка индекса кеша (`tt-global-state-gw-index`)** при двух главных вкладках разных анкет одновременно. Последствие — лишняя перезапись кеша.

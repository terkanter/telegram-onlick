# Сделано — несколько анкет в разных вкладках (форк)

Постановка — [`input.md`](./input.md), план — [`todo.md`](./todo.md). Платформенная половина — ветка `feat/030-telegram-multiaccount-tabs` в `fanbeast-platform`.

## Что изменилось

- **Группа вкладок по анкете.** Форк читает `?tgAccount=` из адреса iframe (`GATEWAY_ACCOUNT` в `src/util/multiaccount.ts`). Каналы выбора главной вкладки и синхронизации, а также ключ `tt-multitab_*` называются `gw_<анкета>`. Воркер получает анкету в своём `name`. Без `tgAccount` имена прежние.
- **Мост к платформе в каждой вкладке.** Он ставится при старте в `src/index.tsx`, и каждая вкладка шлёт `request-settings`. Ведомая вкладка получает права и размытие от своей страницы платформы. `request-auth` по-прежнему шлёт только главная.
- **Контракт v2** (`src/util/telegramGateway.ts`):
  - `request-auth` несёт `tgAccount` и `requestId`;
  - `auth` с чужим `tgAccount` отклоняется;
  - `auth` с незнакомым `requestId` игнорируется;
  - `ready`, `route-change`, `auth-error` и `form-content` несут `tgAccount`.
- **Токен до обработчика.** `auth`, пришедший до регистрации обработчика, игнорируется. Вкладка сама запросит свежий токен. Использованный токен больше не проигрывается при новом получении роли главной.
- **Смена анкеты.** С `tgAccount` каждый следующий `auth` — переподключение на месте. Анкета внутри iframe не меняется, так что перезагрузки на «смену анкеты» нет.
- **Потеря роли главной.** `GatewayTransport.close()` тихо закрывает сокет, гасит таймеры и отклоняет ожидающие запросы. Его вызывает `TelegramClient.destroy()`, а `destroy` в воркере сбрасывает транспорт и флаг пост-коннекта. `resetGatewayAuthFlow()` снимает таймер переподключения, ожидаемый запрос и обработчик `auth`.
- **Переподключение с другой анкетой.** Если id аккаунта гейтвея после переподключения другой, воркер шлёт `updateGatewayAccountMismatch`, и вкладка перезагружается. Кеш прежней анкеты больше не удаляется. Если `tgAccount` не совпал с id из `ready` гейтвея, пишется ошибка в лог.
- **Остановка гейтвея во всех вкладках.** Причина остановки (`revoked` или `error`) хранится в `global.gatewayStopReason`. Поле не кешируется, а между вкладками группы синхронизируется. `App` и `GatewayPending` читают его оттуда вместо сигнала.

## Проверка

- **Типы и линтер.** `tsc` и `eslint` по изменённым файлам проходят.
- **Сборка.** Сборка гейтвея проходит.
- **Headless Chromium.** Проверено на поддельной платформе (протокол v2) и поддельном гейтвее, который отвечает `ready` и считает сокеты по анкетам. Вкладки A, B и снова A открывались в одном профиле.

| Проверка | Результат |
|---|---|
| Открытые сокеты при вкладках A, B, A | A: 1, B: 1 |
| Вторая вкладка A | не запрашивает токен, шлёт только `request-settings` и получает настройки |
| Закрытие главной вкладки A | вторая сама запросила токен; у A снова один открытый сокет, B не затронута |
| Режим без `tgAccount` | вторая вкладка попадает в группу первой, как раньше |
| Одна вкладка без `tgAccount`, старая платформа шлёт `auth` другой анкеты | одна перезагрузка, сокет прежней анкеты закрыт, новой открыт |
| Ошибки `[tg-gw]` в консоли | нет |

У первой вкладки в чистом профиле два запроса токена. Это штатная перезагрузка при установке сервис-воркера.

## Проверка на dev

24.09.2026 платформа с циклом 030 открыла форк как `telegram-onlk-dev.vercel.app/?tgAccount=3a04d545-…#<маршрут>`. Гейтвей прислал в `ready` тот же UUID. Первая синхронизация прошла без выброшенных апдейтов, живые апдейты применяются. Ошибки о расхождении анкеты в логе нет.

## Ограничения

- **Память маршрута в ведомой вкладке.** Ведомая вкладка не шлёт `route-change`, потому что `ready` отправляет только главная. Маршрут ведомой вкладки не запоминается.
- **Уведомления сервис-воркера** по-прежнему не различают анкеты. Это вынесено из цикла, см. [`input.md`](./input.md).
- **Потеря роли без закрытия вкладки не проверена в браузере.** Её трудно воспроизвести синтетически. Путь проверен по коду.

# Бэкенд — аналитика по Telegram-клиенту

Пять метрик по каждой анкете и сотруднику: часы, чаты, ответы после суток ожидания, среднее время ответа, непрочитанное. Клиент шлёт факты кадрами в уже открытый сокет — ручек для отправки нет, сотрудника и анкету сервер знает по соединению. Считает и группирует сервер.

**Пока клиент не шлёт события, отчёт отдаёт нули** — экран можно собирать параллельно.

---

## Кадры от клиента

**back:** Готово.

```json
{ "type": "events", "events": [ … до 500 штук … ] }
{ "type": "unread",  "at": 1755100812345, "chats": 4, "messages": 17 }
```

Внутри `events` два вида, вперемешку:

```json
{ "kind": "presence", "at": 1755100800000, "seconds": 37 }
{ "kind": "message",  "at": 1755100812345, "chatId": "7841…", "messageId": 6789, "out": true }
```

Ответа на кадры нет, `at` везде в миллисекундах.

front:
- `presence` — раз в минуту, пока вкладка **видима**; `seconds` 0–60. Свёрнутое окно не слать. Шлёт главная вкладка.
- `message` — на каждое отправленное и полученное. `messageId` брать через `getMessageServerKey`. **Исходящее шлёт только вкладка-отправитель** (заполнен `previousLocalId`) — иначе автором запишется не тот сотрудник. Входящие шлют все вкладки, повторы гасятся.
- `unread` — отдельным кадром при каждом изменении сводных счётчиков непрочитанного.
- **При подключении досылать историю**: после загрузки диалогов отправить `message` по последнему сообщению каждого чата.

⚠ **Поле `unread` у события `message` больше не принимается** — время ожидания сервер считает сам.

⚠ Без досылки при подключении не видна переписка, пришедшая при закрытой вкладке, и метрики из пунктов 2–4 занижены незаметно: цифры выглядят правдоподобно.

⚠ Молча отбрасываются: события из будущего, всё сверх 500 в кадре, кривые поля, `presence` старше суток. `message` принимается за 30 дней.

## Чтение

**back:** Готово.

```
GET /telegram-stats?organizationId=…&teamId=…&from=…&to=…
GET /telegram-stats/unread?organizationId=…&teamId=…
```

Право `stats.telegram.view` (группа `stats`), в роль Admin не входит. `from` / `to` включительно, всё кроме `organizationId` необязательно. Новых кодов ошибок нет.

Отчёт — два списка: `accounts` по анкетам и `members` по сотрудникам. У сотрудника вложенный `accounts` — его анкеты. Набор метрик одинаковый на всех трёх уровнях.

```json
{
  "accounts": [ { "telegramAccountId": "…", "username": "solar_fansly", "seconds": 25620, … } ],
  "members": [
    {
      "memberId": "…", "username": "ann", "email": "…", "firstName": "Аня", "lastName": "Кравец",
      "seconds": 22300,
      "accounts": [
        { "telegramAccountId": "…", "username": "solar_fansly", "seconds": 22300, … },
        { "telegramAccountId": "…", "username": "sydney_of",    "seconds": 0, … }
      ],
      …
    }
  ]
}
```

⚠ Цифры в отчёте обновляются раз в 5 минут, непрочитанное — сразу.

---

## 1. Часы в каждой анкете

**back:** Готово. `seconds` — секунды с видимой вкладкой, часы = `seconds / 3600`. Список анкет сотрудника берётся из назначений, а не из наработанного: назначенная анкета без активности видна с нулём. Сортировка по `seconds` убывающая применена на обоих уровнях.

front: таблица от сотрудников, по клику раскрытие с его анкетами; сумма на строке сотрудника, разбивка внутри. Подпись строки собрать из `firstName` / `lastName` / `username` / `email` — что есть.

⚠ Сотрудник без единой назначенной анкеты в список не попадает. Деактивированный попадает, только если в выбранном окне у него есть часы.

---

## 2. Новые и возобновлённые чаты

**back:** Готово. Единица измерения — чат, а не сообщение: три сообщения в один чат за день это один чат и три сообщения.

| Поле | Чат |
|---|---|
| `chatsStartedByUs` | появился в этот день, первыми написали мы |
| `chatsResumedByUs` | был раньше, в этот день первыми написали мы |
| `chatsStartedByThem` | появился в этот день, первым написал собеседник |
| `chatsResumedByThem` | был раньше, в этот день первым написал собеседник |

Четыре счётчика взаимоисключающие, сумма равна числу чатов с активностью за день. Объём переписки отдельно — `messagesSent` и `messagesReceived`.

front: решать, новый чат или существующий, не надо — вердикт выносит сервер.

⚠ Прежние восемь полей по сообщениям (`outgoingNewAllTime` и остальные) из ответа убраны.

---

## 3. Ответы тем, кто ждал дольше суток

**back:** Готово. `chatsAnsweredAfterWait` — сколько чатов ждали ответа больше 24 часов и в итоге его получили. Ожидание считается от первого сообщения собеседника, оставшегося без ответа, поэтому повторное напоминание отсчёт не обнуляет.

front: метрика невнимательности, ноль — это хорошо. Сортировать как список претензий, а не достижений.

⚠ Чаты, которым не ответили вовсе, сюда не попадают — их видно только через непрочитанное.

⚠ Поле `outgoingToUnread` из ответа убрано.

---

## 4. Среднее время ответа

**back:** Готово. В среднее идут ответы быстрее часа, остальные не учитываются.

| Поле | Что значит |
|---|---|
| `avgReplySeconds` | среднее в секундах; `null`, если данных нет |
| `repliesWithinWindow` | сколько ответов вошло в среднее |
| `repliesTotal` | сколько всего было пар «сообщение собеседника → наш ответ» |

front: показывать среднее **только вместе с долей** `repliesWithinWindow / repliesTotal` — например «4 минуты по 62% ответов». Гасить строки с малым `repliesTotal`.

⚠ Без доли число вводит в заблуждение: тот, кто быстро отвечает трети обращений, покажет то же среднее, что и отвечающий почти на все.

⚠ Ответом считается любое исходящее, включая стикер.

---

## 5. Непрочитанное

**back:** Готово, без изменений.

```json
{ "accounts": [ { "telegramAccountId": "…", "username": "solar_fansly", "unreadChats": 4, "unreadMessages": 17, "reportedAt": "…" } ] }
```

front: колокольчик у каждой анкеты; ручка лёгкая, опрашивать можно часто.

⚠ Клиент отключился — висит последнее значение, не ноль.

---

## Оговорки

- рабочее расписание не учитывается: ночь и выходные идут наравне. На среднее время ответа почти не влияет, на метрику из пункта 3 влияет;
- входящее записывается тому сотруднику, чей клиент о нём сообщил: при посменной работе на одной анкете новый входящий чат достанется тому, у кого открыта вкладка;
- цифры пересчитываются только за последние двое суток: событие, присланное за более ранний день, в цифры того дня уже не попадёт;
- события хранятся 180 дней, за более ранние даты отчёт пустой.
